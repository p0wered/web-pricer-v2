# Замеры: старая версия против новой

Критерий скорости в проекте относительный (см. PLAN.md §1, §8): обе версии замеряются
на одной машине, на одном файле `Pricer.xlsm` и одном наборе запросов, а результат
оформляется как «было / стало».

## Условия

| Параметр       | Значение                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------- |
| Машина         | MacBook (Apple Silicon), Docker Desktop: 10 CPU, 7,7 ГБ RAM                                                         |
| Данные         | `Pricer.xlsm` от 28.09.2026: 52 МБ, 157 листов, ~1,65 млн строк                                                     |
| Набор запросов | [`tools/benchmark/queries.json`](../tools/benchmark/queries.json), 47 запросов в 6 группах                          |
| Старая версия  | `../web-pricer` @ `c81ba88`, Docker Compose как в репозитории (PHP 8.4-fpm + nginx + MySQL 8.4), без изменений кода |

## Методика

**Импорт.** Файл отдаётся локальным HTTP-сервером с Basic Auth
([`tools/benchmark/serve-file.mjs`](../tools/benchmark/serve-file.mjs)) — имитация DAV.
Перед импортом контейнеры перезапускаются, после импорта снимается пиковая память
контейнеров (`/sys/fs/cgroup/memory.peak`) и общее время.

**Поиск.** Скрипт [`tools/benchmark/search-old.mjs`](../tools/benchmark/search-old.mjs)
логинится и отправляет ровно тот запрос, который делает страница поиска старой версии
(Inertia XHR с частичной перезагрузкой пропсов). Время — от отправки запроса до получения
всего тела ответа. Перед каждым раундом кэш выдачи сбрасывается (`php artisan cache:clear`),
поэтому для каждого запроса есть:

- **холодный** замер — первый запрос, без кэша (так ищет пользователь новый запрос);
- **тёплый** замер — повторный запрос, из 15-минутного кэша старой версии.

В таблицах — медиана по 3 раундам. Отрисовка в браузере в этих цифрах не учитывается.

### Как воспроизвести замер старой версии

1. Выгрузить копию старого проекта, не трогая оригинал:
   `git -C ../web-pricer archive HEAD | tar -x -C <папка>`.
2. В копии: создать `.env` из `.env.example` (сгенерировать `APP_KEY`, указать `DB_USERNAME` /
   `DB_PASSWORD` из `docker-compose.yml`) и сменить внешний порт nginx на `9090`, чтобы не
   занимать `9091`.
3. `docker compose -p oldpricer up -d --build`, остановить контейнер `laravel_scheduler`
   (чтобы не запустил импорт посреди замеров), выполнить `php artisan migrate --force` и
   `php artisan db:seed --force` в контейнере `app`. Для браузера скопировать
   `public/build` из контейнера в копию — nginx отдаёт ассеты с хоста.
4. Запустить `serve-file.mjs` с тестовыми `BENCH_USER` / `BENCH_PASS` и прописать в
   `import_settings` URL `http://host.docker.internal:8089/Pricer.xlsm` и эти учётные данные.
5. Импорт: перезапустить `app` и `webpricer_db`, выполнить `php artisan import:excel`,
   снять время и `/sys/fs/cgroup/memory.peak` обоих контейнеров.
6. Поиск: `OLD_PASSWORD=<пароль из сидера старой версии> node tools/benchmark/search-old.mjs
http://localhost:9090 3 docs/benchmark-results/old-search.json`.

## Результаты старой версии (29.09.2026)

### Импорт

| Показатель                                           |                             Старая версия |
| ---------------------------------------------------- | ----------------------------------------: |
| Время полного импорта (скачивание + разбор + запись) |                                     228 с |
| Пиковая память контейнера `app` (PHP)                | 7,1 ГБ — почти весь лимит Docker (7,7 ГБ) |
| Пиковая память контейнера `db` (MySQL)               |                                    0,4 ГБ |
| Загружено строк: детали / стоп-лист                  |                        1 604 606 / 44 823 |
| Цен в деталях без числового значения (`NULL`)        |                                   460 097 |

Пик памяти вызван загрузкой всей книги в память (`IOFactory::load`). На сервере с меньшим
объёмом памяти импорт упадёт.

### Поиск (сервер, 47 запросов, медиана 3 раундов)

| Показатель                                                     |           Старая версия |
| -------------------------------------------------------------- | ----------------------: |
| Медиана холодного запроса (без кэша)                           |                1 026 мс |
| Диапазон холодных запросов                                     | 994–1 341 мс (успешные) |
| Медиана тёплого запроса (из кэша)                              |                   10 мс |
| Запросы, завершившиеся ошибкой                                 |  **6 из 47 (HTTP 500)** |
| Максимальный размер ответа                                     |       5,6 МБ (`разъем`) |
| Находки по запросам латиницей (`KT315`, `K52-1 50в`, `2PMT22`) |                       0 |

**Почему холодный запрос всегда ~1 с.** Любой запрос — это полный перебор 1,6 млн строк
через `LIKE '%…%'`, поэтому даже запрос с 3 находками занимает около секунды.

**Почему 6 запросов падают.** Широкие запросы (`к52`, `к50`, `к10-17`, `с2-33`, `млт`,
`2рм`) находят 12–95 тыс. строк. Выдача целиком сериализуется в кэш-таблицу MySQL и не
помещается в колонку: `SQLSTATE[22001]: Data too long for column 'value'`. Раз кэш не
записывается, такие запросы падают при каждой попытке — пользователь видит окно «500 SERVER
ERROR» и не может найти, например, все К52.
